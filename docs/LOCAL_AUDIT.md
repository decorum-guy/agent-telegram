# Локальная приёмка Agent Telegram

Цель — проверить схему одного бота и фактически установленную копию в локальном Codex. Этот документ — **сценарий**, а не отчёт о проведённых действиях.

## Точная исходная версия

Перед аудитом получите актуальную опубликованную версию из нового клона после очистки истории. Запишите `git rev-parse HEAD`, ОС, `node --version`, `codex --version`; эти данные не должны включать личные пути. Читайте `AGENTS.md` и текущий отчёт. Не объединяйте разные версии в один результат PASS.

```sh
git fetch origin
git switch main
git pull --ff-only
node tests/run.mjs
```

При чужих локальных изменениях используйте отдельный checkout/worktree; ничего не сбрасывайте. Прежнюю историю не следует сливать с очищенной. Схема не должна возвращаться к разным ботам.

## 1. Статический и автономный аудит

Проверьте общий секрет/реестр, атомарные блокировки, маршрутизацию, смену активного проекта, сохранение offset/очередей, привязку к точному диалогу, секреты и инструкции. Основной набор тестов не должен обращаться к настоящему Telegram, запрашивать модель или ставить службу.

Особенно проверьте:

- Одновременно два процесса получения обновлений не вызывают `getUpdates` одного бота.
- Противоречащие тема/хештег/ответ и чужой отправитель не становятся заданиями.
- Вложения попадают в папку адресата, а не в папку того процесса, который оказался poller.
- Одноразовое подтверждение переключения single отделяет старые личные сообщения от нового проекта.
- Один токен не заменяется переменной окружения или новым token-file без явной процедуры.
- Разные старые боты не объединяются молча; история сохраняется.
- Неподтверждённый runtime, receipt или ACK не помечаются как выполненная работа.

## 2. Установка плагина

```sh
codex plugin marketplace add decorum-guy/agent-telegram
codex plugin list --marketplace agent-telegram
```

В Desktop откройте **Плагины → Agent Telegram → Установить**. Запишите версию и источник; полный локальный путь загруженного skill сохраните приватно. Подтвердите запуск программ именно из установленной копии, их совпадение с кандидатом и отсутствие `.git`, личных настроек и разработческих отчётов в пакете. Если каталога нет, согласуйте перезапуск с владельцем.

Начните новую именованную тестовую задачу в отдельном временном git-проекте. Попросите подключить Telegram обычным текстом. PASS: агент сам спрашивает о параллельной работе, предлагает одного бота, переиспользует существующие настройки и не просит секрет в чате.

## 3. Настоящий Telegram

Проводите обмен только в согласованном владельцем тестовом месте. Сам аудит не разрешает писать посторонним пользователям, менять чужих ботов или заменять действующую установку. Используйте один выделенный бот для всего сценария, одну группу для parallel и безопасно сохранённый локальный токен.

| Проверка | Наблюдаемый PASS |
| --- | --- |
| Первая привязка | Нужный владелец проходит код; посторонний `/start` не присваивает бота |
| single | Отчёт в личке; ответ прочитан нужным тестовым агентом; группа не требуется |
| Переключение single | Старое непрочитанное сообщение не становится заданием нового проекта; одноразовый код подтверждает границу |
| parallel, проект A | Отчёт и ответ только в теме A, с хештегом A |
| parallel, проект B | Тот же бот и группа; отдельная тема B; сообщения не видит A |
| Конфликт | Чужой тег в теме A, неверная группа и неверный отправитель не запускают работу |
| Перезапуск | Уже сохранённые правки доступны после перезапуска; подтверждённые события не исполняются заново |
| Вложение | Файл адресован правильному проекту; недоступный формат не выдаётся за прочитанный |
| Новый чат | Агент узнаёт короткое правило проекта и существующего бота без повторного большого промпта |

Проверку реального обмена отделяйте от `--dry-run`/`--simulate`. Запишите подтверждённые факты без токена и личной переписки.

## 4. Фактический контекст модели

Во время активного хода отправьте из Telegram правку со значением, которого нет в исходном запросе. Сопоставьте отметку отправки, вывод `--checkpoint`, подтверждение `--received` из того же чата и следующий результат работы. Проверьте итог с `tg.mjs --final`. В parallel убедитесь, что отличающиеся правки не прочитаны соседним диалогом. Для проверки перезапуска сохраните входящее, завершите процесс приёма и проверьте повторное чтение до ACK и отсутствие повтора после ACK.

При модельной проверке используйте максимум два именованных тестовых чата A/B, модель `gpt-6-luna` с усилием `low`. Запишите их ID в приватный манифест. Постоянный мост проверяется отдельно при явном запросе. Его диагностика описана в [BRIDGE.md](BRIDGE.md).

## 5. Очистка и отчёт

Отключите только свои тестовые привязки, задачи и процессы. Архивируйте созданные чаты, подтвердите отсутствие активных тестовых обработчиков и не стирайте историю. Не завершайте общий daemon или чужие сессии. При незавершённой очистке следующий модельный тест не начинать.

В публичный отчёт включайте только обезличенные технические результаты, без реальных ID диалогов, локальных имён пользователей и текста Telegram-переписки. Исходные свидетельства сохраняйте отдельно с закрытым доступом.

В отчёте укажите:

1. SHA, среду и результаты автономных проверок.
2. Факт установки плагина и наблюдаемый onboarding.
3. Для каждого живого сценария: PASS / FAIL / BLOCKED с наблюдаемым основанием.
4. Найденные баги, воспроизведение, исправляющий коммит и результат повторной проверки.
5. Число созданных/архивированных чатов, состояние тестовых процессов и оставшиеся ограничения.
6. Заключение отдельно по коду, реальному Codex/Telegram и публичному выпуску.

Официальная публикация не входит в задачу: распространение идёт через GitHub. Изменение видимости, Git-истории и действующих установок требует соответствующего разрешения. Порядок распространения — [PUBLISHING.md](PUBLISHING.md).

## Короткая оставшаяся проверка

Для упаковки 0.1.2 сначала подтвердите фактически установленную версию и состав пакета. Затем в одном видимом чате выполните согласованный обмен: начало → неизвестное модели слово из Telegram → изменение тестового файла → `--received` → настоящий `--final`. Отсутствие входящего слова в окне ожидания отмечайте как BLOCKED. Проверка `--dry-run` подтверждает только формат. Полную матрицу single/parallel повторяйте при изменении соответствующего поведения или новой найденной ошибке.
